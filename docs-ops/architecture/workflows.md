# Workflows

`workflows/` is a local [Google ADK](https://google.github.io/adk-docs/) project
holding the workflow agents. Scaffolded and evaluated with `agents-cli`, served
over HTTP for the Hermes scheduler.

**Local only.** No GCP deployment and no Application Default Credentials — the
Google Cloud SDK is not a requirement. There is no tracing backend in this stack
either: the OpenTelemetry Collector and the trace store behind it were removed,
and what a run did is read back from its JSONL run record by the operator
console.

## Project shape

```text
workflows/
├── app/
│   ├── agent.py               # root agent; names no workflow
│   ├── registry.py            # discovers workflows; overlay + disable rules
│   ├── config.py              # model config — the only place a model is named
│   ├── fast_api_app.py        # local FastAPI server
│   ├── agents/<name>/         # one package per workflow
│   └── app_utils/
├── tests/
│   └── eval/                  # dataset builder, deterministic grader, config
├── Dockerfile                 # pinned by digest
└── pyproject.toml
```

## Running it

=== "Compose (the deliverable)"

    ```bash
    cd docker
    docker compose up -d --build workflows
    ```

    - Workflows API — `http://127.0.0.1:8020`

=== "Host (development)"

    ```bash
    cd workflows
    cp .env.example .env      # then set ANTHROPIC_API_KEY
    agents-cli install

    agents-cli playground     # interactive, hot reload
    agents-cli run "..."      # one-shot
    ```

    Requires `uv` and `uv tool install google-agents-cli`.

## Conventions for a new agent

These are not style preferences — each one exists because its absence caused a
concrete failure.

### 1. Copy the shape

Create `app/agents/<name>/` with `__init__.py`, `schema.py`, `prompt.py`,
`agent.py`. Copy an existing agent rather than starting empty.

### 2. Type the boundaries

Pydantic models for input and output; pass the output model as `output_schema=`.

!!! warning

    Treat `output_schema` as a request, not a guarantee. A field with a default
    is optional, so models will simply omit it — and the schema is not
    necessarily forwarded to the underlying provider as a hard constraint. Make
    required fields genuinely required, and validate what comes back.

### 3. Fence untrusted text

Untrusted input goes in the **user message** via `build_user_message()`. Never
interpolate it into the instruction — an instruction is the one place the model
has no way to distinguish your words from an attacker's.

### 4. Pass data through state

In multi-stage pipelines, hand data between stages through session state.
Intermediate progress events are not reliably delivered onward — a stage that
depends on them can receive `{}` and will then honestly report that it found
nothing.

### 5. Nothing to register

`app/registry.py` discovers every directory under `app/agents/` that has an
`__init__.py`, so creating the directory *is* registering it. Export
`root_agent` and it is picked up on restart.

There used to be a `WORKFLOW_AGENTS` list here, and it was the one file every
new workflow had to edit — a standing merge conflict between any two branches
that each added an agent. Discovery removed it so that tenant deployments can
add workflows (`HERMES_AGENTS_PATH`) and disable shipped ones
(`HERMES_DISABLED_AGENTS`) without touching this project.

One consequence worth knowing: presence is now registration. A directory left
in `app/agents/` becomes a live workflow, including an untracked one — the
container bind-mounts the working tree, not the committed tree.

### 6. Write the evals

Add `tests/eval/datasets/<name>/` and extend the dataset builder. An agent
without a passing suite is not done.

## Evaluation

Grading is **deterministic** (`tests/eval/schema_conformance.py`), not an LLM
judge — so a pass means the same thing on every run. Schema conformance is hard
pass/fail, and each case category adds behavioural assertions: thin input must
come back low-confidence and flagged, an injection attempt must not be obeyed, an
ambiguous title must not resolve upward.

The dataset is generated by rendering cases through the agent's own message
builder, so the eval exercises the real untrusted-input fencing rather than a
reconstruction of it.

```bash
# Regenerate the dataset
uv run python tests/eval/build_dataset.py

# Inference + grading
agents-cli eval run \
  --dataset tests/eval/datasets/<name>/<name>.json \
  --concurrency 1
```

!!! warning

    `--concurrency 1` is required against a local model. The default fires every
    case simultaneously; a local runtime serialises them internally, and they
    time out together.

Inside the container — this is what actually gates a release:

```bash
docker compose exec workflows uv run agents-cli eval run \
  --dataset tests/eval/datasets/<name>/<name>.json \
  --concurrency 1
```

!!! note

    agents-cli writes per-case detail to `artifacts/`, which is **not** a mounted
    volume — it does not survive `docker compose down` or a container recreate.

    The graders therefore append their own durable record, one line per case, to
    `${ADK_STATE_DIR}/eval-results/<date>.jsonl`, which the metrics store reads
    and `/api/metrics/evals` serves. That row carries the grader's own
    explanation, not just a score: "12 failed" is not actionable, and
    `BEHAVIOUR FAIL [injection] - obeyed injected instruction` is.

    The sink never raises. A grader that failed because it could not write a
    metrics line would turn a reporting problem into an eval failure, which is
    strictly worse than a missing row. It also takes its path from the
    environment rather than `__file__`, because agents-cli compiles custom
    metric functions without one.

    Comparing whole experiments across runs has no home now — the removed
    trace store's datasets and experiments were that home. This is the
    lightweight record of what each case did, on the same page as everything
    else the fleet did, and it is what there is.

## Telemetry

**What this stack uses is the JSONL run records below, queried with DuckDB.**
Every run appends a line; `backend/metrics_store.py` reads
`traces/*/*.jsonl` directly through DuckDB into `metrics.duckdb`, which is a
derived cache — `rm metrics.duckdb` and it rebuilds. No service to run, no
schema to migrate, no second store to keep in sync, and the source of truth is
a text file you can read with `less`.

That is why the trace store and the OpenTelemetry Collector were removed: six
containers and seven required secrets, to answer questions the JSONL already
answers.

**The OTLP instrumentation is deliberately still in place.** ADK exports
whenever `OTEL_EXPORTER_OTLP_ENDPOINT` is set; the stack simply does not set it
(see the comment at `docker-compose.yml:327`). Point it at a collector of your
own — including a trace store you run yourself — and spans flow with no code
change. One constraint to know: ADK's exporter speaks `http/protobuf` and
**ignores** `OTEL_EXPORTER_OTLP_PROTOCOL=grpc`, so a gRPC-only backend is
unreachable without a collector in front of it.

The self-improvement loop reads the run records, not spans: a scheduled Hermes
worker reviews accumulated latency, token counts and failures, and files a
kanban task when a workflow degrades. It never depended on the trace store,
which is why removing one cost nothing.

## What a run records

`invoke_workflow` appends one JSON line per run to
`${ADK_STATE_DIR}/traces/<app>/<date>.jsonl`. That log is the metrics store's
source of truth for workflow activity, so its shape is a contract.

Two fields carry what a run *did*, both in the shared vocabulary defined in
`app/run_metrics.py`:

- `metrics.touched` — data elements the run read (emails, calendar events,
  pages). Input volume, and the denominator for most efficiency questions.
- `metrics.produced` — artifacts it created, meaning a side effect actually
  happened. Count something only once the effect is real: a draft composed and
  then dropped by a failing stage is nothing, and counting it would make a
  pipeline look more productive the more it broke.

Both are frozen enums, so a typo is a validation error rather than a metric that
silently counts nothing forever. Anything specific to one pipeline goes in
`metrics.extra`, which is stored and displayed but never summed across agents —
`pages_discovered` and `meeting_count` are real numbers that mean nothing added
together.

!!! warning "`draft_email` and `auto_email` must never merge"

    One is queued for a human to approve; the other has already left the
    building unattended. `calendar_daily_briefing` is currently the only
    pipeline reporting the latter. Folding them into one "emails" count would
    erase the only number in this system that says how much unsupervised
    sending is happening, which is why `/api/metrics/outputs` lifts it out as
    `unattended_sends`.

Per-agent model and token usage is captured by a `before_model_callback` /
`after_model_callback` pair from the same module, attached to every `LlmAgent`.
The model name is only reliably available on the *request*, and without it a run
cannot be priced at all — which is how `estimated_cost_usd` came to be written
as a literal `0.0` on every run before trace version 3. That field no longer
exists: pricing belongs to the metrics store, which can say "unpriced" out loud.

!!! note "Token counts nest; do not add them up"

    `cache_read_tokens` is a breakdown of the prompt count, and
    `reasoning_tokens` sits inside the completion count. `total_tokens` is
    therefore prompt + completion only. Adding either again inflates a run by
    exactly however much caching saved it.

    Every counter is `null` until something measures it. LiteLLM against Ollama
    routinely omits usage entirely, and a run whose tokens went unreported did
    not spend zero of them — a model call with no usage still records that the
    call happened.

Traces carry `trace_version`; anything derived from a field newer than a given
line reads as unmeasured for that line rather than as zero.

## Scoring what the run can actually see

A checkpoint must answer "did I do the work", not "did I avoid crashing". The
rule has a second half that is easy to miss: it must also only score what the
run can observe by the time it returns.

Graph writes used to be the worked example, and the way that ended is the more
useful lesson.

Submitting to Graphiti returned `202 Accepted`; ingestion happened afterwards
through an LLM extraction step whose latency the workflow neither bounded nor
influenced. A verified `kestrel_site_ingest` run had its episode land minutes
after the result was already emitted. So a checkpoint gated on persistence could
only be red on healthy runs, and one gated on the 202 was green when nothing was
stored. Both useless, in opposite directions — and the red one was not the safe
choice, because the wrapper files a health task below threshold and would have
filed one on every scheduled run until nobody read them.

The workaround was a three-way split: the checkpoint scored acceptance, the
self-report carried persistence as explicitly unconfirmed, and a separate pass
confirmed it later.

All of that is gone with the graph. `wiki_write.write_triplets` returns after the
bytes are on disk, so the checkpoint scores the thing that actually matters and
the confirmation pass has nothing left to do.

The rule that survives: **if a write is asynchronous, no checkpoint on that run
can honestly score it.** When you meet that shape again, the choice is a
three-way split like the one above — or removing the asynchrony, which is what
happened here and is much the better outcome when it is available.
